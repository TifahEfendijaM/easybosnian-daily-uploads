# Multiple independent batches

## Semantics

The form exposes batch_target=latest/none/all_today. latest replaces exactly the newest complete saved batch by created_at and created_order (D1 insertion order), keeping its batch_id/date and creation order. none adds a new UUID batch for the current Sarajevo date, without deleting or overwriting any earlier content, artwork or publication IDs. The latest source may supply same_words/same_theme/custom defaults for all targets (all_today prefers a complete current-date source). The four selection rules and fresh text/design generation stay intact. Explicit retained terms may repeat across independent copies; new terms compare against every batch. latest overwrites only its selected content, removing that version’s old novelty terms; none keeps them.

After midnight, latest can replace yesterday’s batch; none is an additional batch for today. The automatic 05:00 dispatch sends daily/none, with default selection new. It adds the morning’s batch even if a manual addition was saved earlier that date. New previews and failed unpublished candidates do not enter history or become a latest source. Existing legacy rows remain readable without adding a publication-state gate. Neither preview nor verify deletes/posts.

## Migration 0005

history’s date primary key becomes batch_id. Keep date as a nonunique indexed content date. Add created_at, assigned once by the Worker; expose rowid as created_order for timestamp ties. Existing rows receive deterministic legacy-YYYY-MM-DD IDs. Their initial timestamps use available private_review.reviewed_at, converted to UTC, or midnight UTC of the content date. These are estimates because the old table never stored actual creation time. Metadata-only historical imports retain their original content/aliases and do not become renderable batches.

Every publication_ids row keeps its provider/account/date/kind and original rowid, and gains legacy-YYYY-MM-DD. Orphan IDs without a content row are retained. Historical same-date content versions already overwritten before this migration cannot be recovered; no old Git artifact or rejected package is restored. Legacy ID buckets may contain several historical publication sets, so cleanup still selects only their last feed and following up-to-three Stories, never all old items. New batches’ IDs are independent from the outset.

No live content, known ID or cron claim is dropped. The obsolete physical table layouts are replaced, not their data. Public URLs and their 14-day expiry stay intact. Migrated private image caches remain readable through a legacy fallback until replacement/expiry; replacement invalidates only its own ID namespace and, for that exact legacy row, its former date namespace. Another batch on the same date never uses or invalidates that fallback. No publication state, hash, revision, reservation, queue, reconciliation, watchdog or retry is added.

## Backward compatibility

GET /v1/history retains its days list, now with one entry per batch, including duplicate dates, plus batch_id/created_at/created_order and storage_version=2. New protected paths are /v1/history/batches/{batch_id}, /v1/publications/batches/{batch_id}, /v1/private/batches/{batch_id}/{name} and /v1/expose/batches/{batch_id}/{name}; generation binds the reviewed prompt to batch_id and date. Existing unambiguous date routes still work; history date reads return that date’s newest row, while ambiguous date writes, publication-ID operations and image generation/storage return 409. They never guess a destructive target. Use explicit IDs for new integrations/imports. The one-time publication-ID importer reads batch_id from current artifacts, or requires --batch-id for ambiguous legacy artifacts; it rejects cross-batch IDs and supports after-midnight replacement dates. The deprecated Python today alias creates a new independent current-date batch but is absent from the form and Worker dispatch.

The publisher reads the private runner candidate using the trusted preparation-result batch ID/date/run identity. Reviewed content is checked for schema/editorial flags/quiz secrecy; full-history novelty, with explicit reuse, is checked during trusted preparation/save. Artifact directories and safe results include batch_id so same-date runs do not collide. No model/provider credential enters these identifiers or logs.

## Replace all current-date batches

batch_target=all_today creates a new UUID batch for the frozen current Sarajevo date. Before research, the trusted wrapper freezes every earlier same-date history batch and every batch with known publication IDs for that date, including IDs whose history was previously erased. It prefers the latest complete same-date row for reuse; if today is empty, it may use the latest complete older row as a source just like none, but never targets that older row for cleanup. All history remains available for novelty/review during preparation and rendering. After rendering, daily attempts the frozen known Instagram feed/Story and Facebook feed cleanup IDs before independent publishing. Only after a feed is confirmed and its new history row is saved does daily remove the frozen earlier same-date history rows and their private artwork, allowing their themes/words to be selected on future runs. If no feed is confirmed or saving fails, earlier history stays intact. It preserves the new row, other dates, and unsupported/uncertain publication IDs; those IDs carry no content novelty and are retained only for ownership-scoped cleanup. Facebook Stories/photos and TikTok remain manual; disabled platforms are not cleaned. Cleanup/history-removal failures warn but do not block independently gated posting. Public random image URLs retain their original 14-day expiry. Empty today behaves like none with no fallback deletion of yesterday. Preview only stages/renders a new private batch without saving history and never removes history or social content; verify remains read-only. No new table, migration, retry, state machine or clock change is needed.

This compatible extension needs no migration. Deploy the Worker endpoints first, verify its unchanged daily/none dispatch and live cron, then merge the updated form. This is separate from the historical migration-0005 cutover described above; do not reapply that cutover or reset the publishing switch for this endpoint-only change.

## Published-only history lifecycle (October 6 update)

The reviewed candidate lives only in `build/reviewed-content.secret` (0600, ignored, not uploaded as an artifact). Its project, batch ID, content date and GitHub run identity must match the trusted preparation result. Private generation sends that reviewed candidate to the authenticated Worker without inserting a D1 history row. Each artwork attempt uses an independent random run-cache namespace; legacy saved-history generation remains readable.

Only a confirmed feed publication on at least one enabled platform saves the candidate in history, immediately before later platforms/Stories continue. This records vocabulary that actually appeared even if another platform or Story fails. Save once, without an automatic retry. Preserve the freshly rendered private assets during this save. If no feed is confirmed, retain the prior history. If history saving fails after a confirmed publication, continue independent publishers and report a failed run with the confirmed publication status; do not republish or pretend history succeeded. Known provider IDs are still recorded immediately, including ambiguous/partial outcomes, using the authenticated explicit batch/date scope even before a history row exists.

For latest, overwrite the selected row only at that confirmed-publication point, retaining its date/creation order. For none, add the new row then. For all_today, prune the frozen older rows only after the replacement feed is confirmed AND its history save succeeds. Existing best-effort social cleanup still precedes publishing after rendering, and cannot block the new post. Previews never save or erase history. No publication state machine, queue, migration, retry or clock change is added. Existing older unpublished/legacy rows are not bulk deleted; today's explicitly identified unpublished failed batch was removed separately.

Deploy the backward-compatible Worker FIRST (inline reviewed generation, explicit staged asset/known-ID date scopes, preserve-artwork save), verify identity/unchanged cron and protected private generation, then merge the client workflow. Older clients remain compatible during rollout. No live publication test, cron reset or catch-up dispatch is needed. Provider failures expose fixed reasons, bounded numeric codes (including undocumented/nested codes) and per-call HTTP status only; raw provider prose is never written into logs or failure issues. Failed staged inference bodies (up to 64K characters, known credentials redacted) are kept only in authenticated private KV for 14 days and a 0600 runner .secret file, excluded from artifacts; one protected diagnostic read is not another inference attempt.
